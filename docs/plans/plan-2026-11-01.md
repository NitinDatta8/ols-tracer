## 1. Healthy runs

On the work machine. Nobody captures by hand: the bridge records each session itself.

1. `git pull`, then `npm install`. Run `npm run bridge:setup` once if `bridge/.venv` is missing.
2. Restart `npm run bridge`. It reads `bridge/poll.json` only when it starts. The list now has 57 commands, 12 of them polled.
3. In the UI, open the physical view and connect to box 3. The connect snapshot runs all 57 commands once (a minute or two).
4. Stay connected for at least 10 minutes, so `poll.jsonl` gets about 60 readings of each 10 s value. That is the healthy noise band.
5. Disconnect.
6. Check the run folder `data/boxes/box3/runs/<YYYYMMDD-HHMMSS>-connect/`: in `meta.json` every `prereqs` entry is `ok: true` and `hostname` and `release` are filled in; in `raw/index.jsonl` note any `ok: false`. Set `meta.json` `state` to `healthy`.
7. Repeat: run A now, run B later today, run C tomorrow, for drift.
8. Optional run D: stop the BERT but keep the light on, and set `state` to `healthy` with `notes: "traffic-off"`. It shows whether the eth counters move with BERT traffic (run 1 suggests the BERT sends PRBS, not frames).
9. Fill in what `setup.md` still asks about the BERT: vendor and model, pattern, remote control.
   Also there: ALS/APR and protection, if you can see them.
10. Commit and push only the data:
    ```sh
    git add data/boxes/box3/runs data/boxes/box3/setup.md
    git commit -m "data: box 3 healthy runs A-C"
    git pull --rebase && git push
    ```

- **Don't rely on typing.** Commands typed in the terminal are not saved until step 9, so everything that matters is in `poll.json`.
- **This is the recorder's first run on real hardware.** It has only run against a fake box that replays run 1. If something looks wrong, keep the folder and write what you saw in `notes`.
- **Read-only.** Every command in `poll.json` is a `show` (and `date-time`, which only prints the clock). The prerequisites set the CLI's paging and width, as before.

What the 57 commands are, by group: [box 3 capture → Capture list](box3-capture.md#capture-list).

### Also on the work machine: two catalog gaps

The catalog is generated from the IIVI profiles, which are only on the work machine (`../IIVI_Platform`), so these are fixed there, in `scripts/sync-linecards-from-iivi.mjs`, then `npm run sync:linecards`:

1. **The 800MX takes no QSFP-DD.** Its ports allow only 100G QSFPs, but box 3 runs a QSFP-DD DCO (FTCD3323R1PCL-1Y) in 1-7-5 with port mode `PROT_ZR400_16QAMSS_60G`, and 1-8-1 is set to `PROT_ZR800_16QAMPS_123P8G`. The sync's service-type match probably misses the ZR modes.
2. **The C1125's LINE takes a pluggable** (60G700001 and others), but box 3 has a plain LC there (`show inventory` lists no transceiver on 1-1). So the F05 loopback can't be drawn until LINE is a fixed port.

Also not in the catalog: box 3's client optic, FS QSFP-LR4-100G (third party). [Step 3](#3-box-3-drawn) draws a stand-in, and [step 8](#8-connect-fills-the-canvas) has to handle third-party parts.

## 2. CLI address map

**Done (2026-11-01).** `cliPort` and `cliAddress` in `src/catalog.ts`; `cli()` uses them. The rule, from what box 3 prints: `PORT<n>` is `<n>`, anything else is lowercased (`AD1` → `ad1`, `OSC` → `osc`). Other cards' names (`C2`, `L1`) are not confirmed on a box yet.

The catalog's port ids are not the box's port names: an 800MX's `PORT4` is `4` on the box, and a C1125's `AD1` is `ad1`. So `cli()` (`src/catalog.ts`) builds `show port 1-7-PORT4` today, and live values can't find their port.

- One function from a catalog port id to its CLI name, used by `cli()` and by everything that keys live values (steps 5, 6, 8).
- A smoke test with box 3's ports: `PORT4` → `1-7-4`, `PORT5` → `1-7-5`, `AD1` → `1-1-ad1`, `LINE` → `1-1-line`.

## 4. Last state when off

**Done (2026-11-01).** `latest()` in `bridge/recorder.mjs`; the shapes are in the [guide](../guide.md#poller).

`/bridge/state` served the poller's latest results while connected and cleared them on disconnect. While disconnected it now answers from the latest run instead: its `parsed/` files, updated by the last line of each command in its `poll.jsonl`.

- The response says which: `{ live: true, commands }`, or `{ live: false, run, at, commands }` with the run's name and when it ended.
- With no box ever connected, run 1 is the latest run, so everything after this works from run 1 on this Mac.

## 5. Live store

**Done (2026-11-01).** `live` in `src/store.ts` holds `/bridge/state` as it comes, and `src/live.ts` reads it by CLI address. It applies only to the device whose `host` is the state's `host`, so box 3's values never land on another topology.

- A store slice, `live`, keyed by CLI address (`1-7-4`), never saved in `.olst.json` (like the alarms).

## 7. Templates

**Done (2026-11-01) for the commands run 1 has:** `show system`, `show software`, `show chassis`, `show card`, `show inventory`, `show card 1-* fan` and `psu`, `show logical-channel`, `show interface`, `show lldp neighbors` and `show log event`, 11 templates with run 1's outputs as fixtures (`npm test`: 53 tests). The rest wait on step 1's runs. If a run was recorded before its templates were pulled, `node bridge/recorder.mjs <run folder>` parses it again.

- **Alternation:** a `|` inside `re("…")` splits TTP's argument, and `\x7c` outside a character class is a literal pipe. A regex with alternation goes in the template's `<vars>` and is named: `re("ADMIN")`.
- **Not needed:** the list forms of `show transceiver`, `show och` and `show eth`. Their ids come from `show inventory` and `show assignment` already.
- **Dropped:** `show transceiver 1-7-* physical-channel`. Its table has no transceiver address, so its lanes can't be told apart; the per-lane commands stay.
- A fixture named `<id>~<form>` tests another form of the same command against the same template.

One template per command id. A list form (`show och`) and its detail form (`show och 1-7-5`) share an id, so a template parses every form of its command that is used. Fixtures come from run 1 where it has the command, and from step 1's runs for the rest.

- `show external-connection` may hold the box's own fiber map. If it does, it is the one place the box says where the glass goes, and step 8 uses it.

## 8. Connect fills the canvas

On Connect to a device with no cards, the bridge's connect snapshot fills it:

- `show card` and `show inventory`: module type → linecard id (`TMUXC1125` → `lc-c1125`, `800MX` → `lc-800mx`), transceiver part number → pluggable id from the catalog's `part`. Anything with no match is listed, not guessed.
- Until the snapshot is done, the chassis is greyed out with "Fetching data from box". The bridge's `/status` says how far the snapshot is.
- Fibers stay drawn by hand unless `show external-connection` or LLDP gives them.

## 9. Recorder parts 5 and 6

From [box 3 capture → The recorder](box3-capture.md#the-recorder):

- **Part 5:** a typed `show` command's final line, read from a headless xterm fed the terminal's output, runs again on the poller's shell and is saved in the latest run. Never `set`, `delete`, `clear`, `commit` or `rpc`.
- **Part 6:** marking a fiber as pulled in the UI writes `answer.json` into the run that the alarm change created. The agent never reads it.
- Built and tested here against a replay of run 1, then checked on the box.

## 10. Pull experiments and the agent

The bridge into the roadm-diagnostic project: the same run layout and scoring.

- **Box:** one pull per run on F01, F03, F04 and F05, each marked in the UI (step 9), each restored, with a healthy run between. F02 ends at the BERT, so its right answer is "insufficient evidence".
- **Here:** the rule-based baseline (the most-upstream LOS on the known path), the agent (one call with the diff against the healthy run, the path and the inventory), and the scorer, which appends to `metrics.csv`.
- Done when the agent beats the baseline and never cites a value that is not in the run.
