## 1. Healthy runs

On the work machine. Nobody captures by hand: the bridge records each session itself.

1. **Update.** `cd ols-tracer && git pull` (at `db890f8` or later), then `npm install`. If `bridge/.venv` is missing, `npm run bridge:setup`. `npm test` should pass.
2. **Bridge.** In terminal A, stop any old bridge and run `npm run bridge`. It reads `bridge/poll.json` only when it starts: 57 commands, 12 of them polled. `bridge/.env` holds the box login.
3. **App.** In terminal B, `npm run dev`, and open http://localhost:5173. `npm run dev` first regenerates the catalog from `../IIVI_Platform`; if `git status` then shows changes under `catalog/`, leave them out of the data commit.
4. **Open box 3.** **Open** → `examples/box3.olst.json`, then click the chassis. Its IP, 10.111.25.12, is filled in. The status line says **Last state · Oct 31, 10:56** (run 1).
5. **Connect.** The dot goes amber, then green. Terminal A prints `recorded data/boxes/box3/runs/<YYYYMMDD-HHMMSS>-connect` once the snapshot is done (a minute or two), and the status line says **Live**. Open the 800MX in slot 7: F03 and F04 show their dBm.
6. **Wait at least 10 minutes,** so `poll.jsonl` gets about 60 readings of each 10 s value. If an alarm changes meanwhile, the bridge records an `-alarms` run too; keep it.
7. **Disconnect.**
8. **Check the run.** In `data/boxes/box3/runs/<run>/meta.json`, every `prereqs` entry is `ok: true` and `hostname` and `release` are filled in. `grep '"ok":false' raw/index.jsonl` lists commands whose prompt never came back. Set `state` to `healthy`.
9. **Repeat:** run A now, run B later today, run C tomorrow, for drift. Optional run D: stop the BERT but keep the light on, and set `notes: "traffic-off"`. It shows whether the eth counters move with BERT traffic.
10. **Fill in `setup.md`:** the BERT's vendor and model, pattern and remote control; ALS/APR and protection, if you can see them.
11. **Push only the data:**
    ```sh
    git add data/boxes/box3/runs data/boxes/box3/setup.md
    git commit -m "data: box 3 healthy run A"
    git pull --rebase && git push
    ```

- **Don't rely on typing.** Commands typed in the terminal are not saved until step 9, so everything that matters is in `poll.json`.
- **This is the recorder's first run on real hardware.** It has only run against a fake box that replays run 1. If something looks wrong, keep the folder and write what you saw in `notes`.
- **Read-only.** Every command in `poll.json` is a `show` (and `date-time`, which only prints the clock). The prerequisites set the CLI's paging and width, as before.

### The L0 profile

The syncs read `profile/cu/platform` (cards and their ports), `profile/cu/l1` (pluggables and service types) and `profile/cu/cli`. Nothing reads an L0 profile. So the L0 cards in the catalog (C1125, C925, TMUXC935, C25, OA25/35, OLA25/35A/35B, the TFF filters, the TWS cards) are only lists of ports, and their amplifier ports (BAIN, LINEIN, LINEOUT, PAOUT) are plain `port`s.

1. **Find it:** `ls ../IIVI_Platform/profile/cu/`, then the L0 folder for CSP if there is one (`ls ../IIVI_Platform/profile/cu/l0/csp`). The CLI index has an `l0` branch, so the CLI side exists (`cli_shortcut_cmds_l0.xml`).
2. **Take only what the tracer uses,** per L0 card:
   - **The internal light path:** which port feeds which (on box 3: AD1 → mux → booster → LINE, and LINE → preamp → demux → AD1). With it, F03 → C1125 → F05 → C1125 → F04 is one path for the wires and for the agent.
   - **Amplifiers:** which ports are a booster's or a preamp's input and output, gain range, maximum output power.
   - **Port power limits and alarm thresholds:** box 3's standing `IN_OPTICAL_HIGH_WARNING` on 1-1-ad1 comes from one. These may give [step 11](#11-threshold-colours) its thresholds, since `show pm threshold` is invalid.
   - **Channel plan:** which add/drop port carries which frequency (AD1 carries 193.5 THz on box 3).
   - **Roles** for the amplifier ports, instead of `port`.
3. **Where:** optional fields on each card in `linecards.json`, written by `scripts/sync-linecards-from-iivi.mjs` (or a new `scripts/sync-l0-from-iivi.mjs` that `sync-all.mjs` runs), with their types in `src/types.ts`. Optional, so nothing else changes.
4. `npm run sync:auto && npm test`, then commit `scripts/`, `catalog/` and `src/types.ts`, and push.

This is the profile's data, as with the L1 cards. Nothing is modelled, and GNPy stays parked.

## 7. Templates

The rest wait on step 1's runs. If a run was recorded before its templates were pulled, `node bridge/recorder.mjs <run folder>` parses it again.

- **Alternation:** a `|` inside `re("…")` splits TTP's argument, and `\x7c` outside a character class is a literal pipe. A regex with alternation goes in the template's `<vars>` and is named: `re("ADMIN")`.
- **Not needed:** the list forms of `show transceiver`, `show och` and `show eth`. Their ids come from `show inventory` and `show assignment` already.
- **Dropped:** `show transceiver 1-7-* physical-channel`. Its table has no transceiver address, so its lanes can't be told apart; the per-lane commands stay.
- A fixture named `<id>~<form>` tests another form of the same command against the same template.

One template per command id. A list form (`show och`) and its detail form (`show och 1-7-5`) share an id, so a template parses every form of its command that is used. Fixtures come from run 1 where it has the command, and from step 1's runs for the rest.

## 14. Box history and fast runs

**Done (2026-11-04),** from what the runs of 2026-11-02 showed: the best of that day happened while nothing was connected, and was found again only in the box's own logs. Checked against a fake box on spare ports, with the runs written to a scratch folder.

- **History:** `bridge/history.mjs` gathers every `show log alarm` and `show log configuration` of a box's runs (snapshots and polls, hand-grouped folders too) into `data/boxes/<box>/history.jsonl`, one event once, with the box's time and the wall clock's (the first run's offset that logged it; a hand capture's last). It keeps what it has, so deleting runs loses nothing from it. The recorder updates it after each snapshot; `node bridge/history.mjs data/boxes/box3` does it by hand and prints the episodes. Box 3's has 918 events, from 2026-10-28.
  - `mediach-ch-6` in the log is `ch-6`, as `show alarm` names it. The recorder's own `set cli length` and `width`, two lines per session, are left out.
- **Episodes:** `episodes()` cuts the history at each thing the box says was done: a `set` or `delete`, an `rpc reboot`, a card taken out (`EQPT_ABSENCE`). Each gets the outage after it (any traffic-hitting LOS or LOF up), the first alarms raised, `backSec` from the action to traffic back, and `restores` on what brought traffic back. An outage nothing explains gets `cause: null`, for a person to label: on 2026-11-02 the client flaps at 11:34–11:54 and the unplugs at 11:59:20, 12:13:27, 12:14:34 and 12:19:32.   - 2026-11-02 in numbers: NE warm reboot, no outage; NE cold, traffic back after 337 s and 372 s; card 1-1 cold, 47 s; C1125 out, 79 s; 800MX out, 296 s and 275 s; a deleted media channel, 22–27 s until the next was set.
