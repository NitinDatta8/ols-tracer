# OLS Tracer guide

How to use OLS Tracer, and how its catalog, rules and code are laid out. To install and run it, see the [README](../README.md). What comes next is in the [roadmap](roadmap.md), and why it is built this way in the [decision log](decisions.md).

React + TypeScript + Vite, React Flow for the canvas, Zustand (+ Immer) for state, plain SVG for the physical view. The web app has no backend. An optional CLI bridge (`bridge/server.mjs`) runs its commands on a lab box over SSH.

To see everything at once: **Open** → `examples/demo.olst.json`.

A pluggable's datasheet in the inspector, opened from a port, shows its command, which is its port's (`show port 1-3-C2`). **Copy** copies it. **Run** types it into the terminal and presses Enter |
| Box | Type the box's IP next to **← Back** and click **Connect**; the device keeps it. The dot is green while the bridge has the box connected, orange while it connects and grey when it is down (the text next to it says why). Closing the view, or the page, leaves the session: the bridge keeps one per box, shared by everyone connected to that box (other views, Codex sessions through the MCP), and closes it once the last of them leaves. **Disconnect** leaves it the same way, so it can stay connected for others (the text's tooltip says how many), and **Connect** then joins it again. A session with another box is never touched. The terminal attaches only while this view holds the session. **Connect on an empty device draws it from the box:** the chassis is greyed out with "Fetching data from box" and how far the snapshot is, then each present card from `show card` and each transceiver from `show inventory`, matched by module type and part number. Each strand whose two ends are box ports is drawn; one that ends off the box (the BERT) is left out, so fiber a BERT tester from the palette by hand, and one the fiber rules refuse is named in the toast |

## Catalog

```
catalog/
  streams.json              # the five corporations (streams): csp, ctc, polaris, tencent, ws
  common/cli.json           # CLI command templates and modes, merged into every stream
  <stream>/                 # chassis.json, linecards.json, pluggables.json, cli.json
  csp/testers.json          # kept by hand: the BERT tester (chassis and linecard), merged into CSP's hardware
```

The stream files are generated from the IIVI profiles in `../IIVI_Platform/profile/cu/`, so don't edit them by hand: the next sync overwrites them. `npm run dev`, `build` and `test` run `npm run sync:auto` first, which does nothing when that folder is missing, so the committed files are used as they are.

| File | Generated from | Script |
| --- | --- | --- |
| `streams.json`, `<stream>/chassis.json` | `platform/<stream>/CHASSIS.json`, plus each card's profile for its width | `npm run sync:platform` |
| `<stream>/linecards.json`, `<stream>/pluggables.json` | `CHASSIS.json` and `l1/<stream>/l1_profile.xml` (its `supported-part-no` lists) | `npm run sync:linecards` |
| `<stream>/cli.json` | `cli/<stream>/cli_shortcut_cmds_eqpt.xml` and `cli_shortcut_cmds_l1.xml` | `npm run sync:cli` |

`npm run sync:auto` runs all three. `npm run sync:cli-data:csp` builds CSP's CLI index from the CLI XML into `data/cli/csp/` (committed), and a box's `cli-observed.json` and `cli-index.merged.json` from its runs (git-ignored); the [CLI data schemas](reference/cli-data-schemas.md) describe them.

- A stream is any profile folder that has all three: `platform/<stream>/CHASSIS.json`, `cli/<stream>` and `l1/<stream>`.
- A stream's hardware files are its whole catalog: `common/` has no hardware. `<stream>/testers.json` adds test equipment the profiles don't have, as `{ chassis, linecards, pluggables }`; no sync writes it, so edit it by hand. A tester chassis has `tester: true` (no box, no CLI, named after itself) and `comesWith` (the cards a new one has in, by slot). Only `cli.json` merges, a stream's overriding `common/`'s level by level.
- Every stream has one chassis today, `ch-8slot`: 8 linecard slots as 4×2, 2 PSUs and 3 fans. `slotDomains` keeps the profile's slot ids by kind (linecard 1–8, psu 21–22, fan 31–33, fp, cu, mux).
- The linecards are the chassis's `supportedVendorTypes` (`TMUXC1125`, `800MX`, …). `vendorTypeMap` gives each its linecard id: known names get readable ids (`lc-c1125`, `lc-800mx`), the rest `lc-<vendor type>` (`lc-tmuxc935`). `linecardMappingComplete` means every vendor type got a mapping, `knownLinecardMappings` and `fallbackLinecardMappings` count each kind, and `knownMappingComplete` is true only when none fell back.
- When the catalog loads (`hydrate` in `src/catalog.ts`), each slot's allowed list also gets every supported card that fits there, a card the profiles name without describing it gets a placeholder (one client port P1, one line port L1), and a port's pluggable family that no pluggable has gets a `<family>-placeholder`.
- A port's `role` comes from its profile module or its name: `line` (`LINEPORT`, `L1`), `client` (`CLIENTPORT`, `C1`), `adddrop` (`AD11`), `com`, `osc`, `monitor`, else `port`. Its `behavior` (`showsInL1`, `showsInData`, `canLoopback`, `serviceGroup`) drives the views and rules; without one, line ports show in L1 and loop back, and client ports show in Data.
- The pluggables are the `supported-part-no` parts, with the lowercase part number as their id (`ftlc1154rdpl`), and their form factor (SFP, QSFP, QSFPDD, CFP2), speed and `dco`.
- Files and autosaves with the old demo ids (`corp-a`, `ch-2000`, `lc-c1`, …) are upgraded when they load (`RENAMED` in `src/store.ts`).
- `chassis.columns` lays the slots out row by row (4 columns → 4×2 for 8 slots). `chassis.category` groups the palette (optional).
- `chassis.psus` and `chassis.fans` are how many PSU and fan bays its back has, named PSU1…PSUn and FAN1…FANn (default none, and then no **Rear** button). A device saves the bays left empty as `emptyBays`, e.g. `["PSU2"]`.
- `chassis.mgmtPorts` lists the management ports drawn in a narrow strip at the left: `front` (USB-C, CON, MON) and `back` (NMS, NMS1, NMS2), where the back shows them left of the PSUs (stacked) and fans. Names starting with `USB` are drawn as USB-C, the rest as RJ-45. They are only drawn: no fibers, alarms or CLI.
- `linecard.width` is how many side-by-side slots a card takes (default 1). It sits in the leftmost one; the slot's allowed list decides where it may start, and it must fit in that row.
- `linecard.columns` lays its ports out row by row, the same at the chassis and at the card level. By default a card's ports sit as in its 1U slot: one row of up to five per slot of width, else two rows, the top one the longer (800MX 5 over 5, 400MX one row of 5, C1125 10 over 10, OCM 5 over 4).
- A port's `allowedPluggables` lists pluggable ids (the profiles list parts) or whole families (`"QSFP"` takes every QSFP). An empty list (`[]`) is a fixed port: built-in SMF Tx/Rx, fibered as is, no pluggable.
- `cli.json` (not a list) holds the CLI command templates per level, `chassis`, `card`, `port` and `pluggable`, with `{chassis}`, `{slot}` and `{port}` filled in. A wide card's `{slot}` is its leftmost slot. A pluggable's command is its port's, `show port …`. A stream's `cli.json` overrides `common/`'s level by level.
- `common/cli.json`'s `terminals`, kept by hand, are the right-click terminals on a card: `telnet` and `engineering` are the lines typed into a new shell, one per step, with `{chassis}` and `{slot}` filled in and `{slot*4}` as the slot times 4 (slot 7 → `telnet 1.0.1.28`); `noTelnet` lists the linecard ids whose Telnet is greyed out. Edit them there; no sync writes them.

- Chassis, linecards and pluggables all carry the same datasheet info, all optional: `vendor`, `part`, `image` (path under `public/`), `url` (a link, or a file under `public/` such as `datasheets/c1125.pdf`), `about` and `specs` (any label → value, shown in the inspector). A pluggable without `image` shows its form factor instead; `dco` groups it under DCO.
- Internal capture and generated CLI data now goes in `data/` (for example `data/cli/csp/` and `data/boxes/<box-id>/`).

## Rules

`src/rules.ts` holds them all:

- Allowed lists: `linecardError` (card in slot; a wide card also needs its neighbour slots free and in the same row) and `pluggableError` (pluggable in port).
- `fiberRules` for a fiber from `a`'s Tx to `b`'s Rx, checked in order: both ports have a pluggable (or are fixed), both are SMF, `a`'s Tx and `b`'s Rx are both free, and the ends are not on the same card, except a line port looping back to itself and a same-card `800MX` LR4↔LR4 daisy chain. To add a rule type, add a function to the list.
- `validate` re-checks a whole topology. It runs on every change, so an opened file's problems are listed.
- `alarms` raises a device's alarms from the topology: LOS on each pluggable with no fiber into its Rx and one per empty PSU or fan bay. They are never saved, so they always match the build.

## Poller

The bridge polls the box for its live state, so the canvas can show it later, and records every session as runs under `data/boxes/<box-id>/runs/` (default box id `paho-gs2000-03`, configurable with `BOX_DATA_BOX` or `BOX_DATA_ROOT`). Nobody has to capture anything by hand.

- `bridge/poll.json` lists what to run: `{ "prereqs": ["configure", "set cli length 0", …], "commands": [{ "cmd": "show och 1-7-5", "every": 10 }, { "cmd": "show system", "every": 0, "fast": true }, …] }`. `prereqs` run once per session, first. The snapshot when the session opens runs all the `commands` once, and those with `every` > 0 are also polled that often, in seconds. The snapshot on an alarm change or a pull runs only the polled ones and those with `fast`. With no commands the poller is off.
- While a box is connected, the poller runs its commands on shells of its own in the session, so it never types into the terminal. Each is a dumb terminal 500 columns wide and 10000 rows tall, so nothing wraps or pages, and runs one command at a time. A command is done when the last line of its output matches `BOX_PROMPT` and nothing more comes for 100 ms. If that takes longer than `BOX_TIMEOUT`, the poller sends Ctrl-C and records that the prompt never came.
- **Workers** (`bridge/shells.mjs`): `BOX_WORKERS` (1 to 8, default 1) is how many shells the poller opens, each a CLI session of the box's own. A snapshot's commands are shared out over them, each to whichever shell is free; the polls, typed commands and pulls stay on the first. The first runs the prerequisites, recorded; then the others run them one at a time, unrecorded, so no two are in `configure` together, and each joins the snapshot once it is set up. A shell that shows no prompt after login or fails a prerequisite is dropped, with a line in the bridge's log. `meta.json`'s `snapshot.workers` says how many shells took part, and the run's raw files are numbered in the order their commands finished. To find the box's best count, connect with 1, 2, 4 and 8 and compare the connect runs' `started` and `ended`: past the box's limit on CLI sessions, shells are dropped, and a box that runs one command at a time anyway gains little.
- `bridge/recorder.mjs` writes a new run folder, `<YYYYMMDD-HHMMSS>-connect`, when the session opens (and when it opens again after a drop), `<YYYYMMDD-HHMMSS>-alarms` whenever a poll of `show alarm` sees the active alarms change, and `<YYYYMMDD-HHMMSS>-pull` when a pull is marked. Each folder holds one snapshot, laid out as in [Runs](#runs), with `wiring.csv`, the box's strands when the snapshot began, which the run is read with later. A run without one, as most from before 2026-11-08 are, is read with the box's. The polls until the next snapshot go into its `poll.jsonl`, each only when it reads differently from the last of its command. A run goes to the box `show system` names: the one whose `setup.md` has the hostname in a table cell, else `data/boxes/<hostname>/`. Threshold warnings and `REACH_MAX_ATT_*` don't count as an alarm change. If a prerequisite fails, nothing is polled, because paging could cut output short.
- **Typed commands** (`bridge/typed.mjs`): the terminal's output also goes to a headless xterm of the same size, so the bridge sees each line as the box left it, after Tab completion, backspaces and history. When Enter is sent and the box echoes it, a `show` command on that line is run again on the poller's shell and recorded in the latest run as `source: "typed"`. Only at the operational prompt (`admin@…>`, not configure mode's `#`), and never with `?` or a `|` pipe; nothing but `show` is ever re-run.
- **A marked pull**: `POST /bridge/pull?host=` with a strand's name from `data/boxes/<box-id>/wiring.csv` (`GET /bridge/wiring?host=` lists them) takes a snapshot into `<YYYYMMDD-HHMMSS>-pull`, with `answer.json` (`{ fault: "pull", strand, from, to, via, markedAt, detectable }`) and `meta.json` `state: "fault"`. `detectable` is false when the strand's Rx end is not a box port (F02, into the BERT), where "insufficient evidence" is the right answer. The agent never reads `answer.json`.
- **A show asked for** (`bridge/show.mjs`, for the MCP's `run_show`, which calls the bridge directly): `POST /show?host=&by=` with one command line runs it on the poller's first shell between its polls, records it in the latest run as a typed show is, `source: "mcp"` with `by` (who asked: `codex:<session id>`), and answers `{ host, cmd, at, ok, raw }` with its parse (`template`, `data` or `error`). The line must pass the typed commands' rule (`showOf`: `show` only, one line of printable text, no `?` or `|`) and be a `show` in the CLI index; anything else gets a 400 that says why, before anything reaches the box. No box connected is a 409.
- **A baseline** (for the MCP's `capture_baseline`): `POST /baseline?host=` takes a snapshot into `<YYYYMMDD-HHMMSS>-baseline`, as a pull does, and once that snapshot is whole sets `meta.json` `state: "healthy"`. It answers with the `meta.json`, or a 409 when no box is connected or the session closed first. Only once the person says the box is healthy: a baseline taken during a fault turns that fault's alarms into noise.
- **A procedure** (`bridge/procedures.mjs`): a box workflow, defined in `catalog/common/procedures.json` (a stream's `catalog/<stream>/procedures.json` replaces one by id), run on a shell of its own in the box's session. `GET /procedure?host=` lists the box's and the one asked for now or last; `POST /procedure?host=&id=&by=`, with its params as JSON, asks for one: a `read` or `reversible` one runs at once, a `change` waits for `POST /procedure/approve?host=&ref=&by=`, which takes the box's hostname typed in its body and only the tracer UI's Origin, and expires after 15 min (`PROCEDURE_PENDING_SEC`). `POST /procedure/cancel?host=&ref=&by=` stops it. One at a time on a box, and it holds the session until it is over. It takes a fast snapshot into `<YYYYMMDD-HHMMSS>-procedure` first, with its `procedure.json`, and one after a reversible or change; its lines go into the session's current run. A step that drops the session (a reboot) expects it, and the runner goes on once the box is back and its connect snapshot whole; a drop anywhere else stops it, saying to check the box. The model is in the [procedures plan](procedures-plan.md#procedures). A box whose prerequisite fails is not polled, so a show, a baseline or a procedure asked of it is refused. The catalog has two so far, both read and at the chassis: **Software audit** (`software-audit`: the release not committed, a candidate left behind, a card on another release) and **Health check** (`health-check`: cards not in or not active, alarms since the box's latest healthy baseline, `NO_CMT_SW`, `DATETIME_UNCHANGED`, a manual config-saving-mode), as in the [plan](procedures-plan.md#5-software-audit-and-health-check). What a verify finds wrong is its result, not a failure: the procedure ends `done`, each finding a `finding` step in its log.
- `node bridge/recorder.mjs <run folder>` parses a run's raw output again into `parsed/`, e.g. after a template changed or for a hand capture.
- `bridge/history.mjs` keeps `data/boxes/<box>/history.jsonl`: every alarm and configuration change in the box's logs, from all its runs, each once, with box and wall time. The recorder updates it after each snapshot, and it keeps its events when runs are deleted. `episodes()` cuts it at each thing the box says was done (a `set` or `delete`, a reboot, a restart: an `activate`, `rollback` or `clear database`, or a card out) with the outage that followed, up to 10 min after it, 30 min after a restart, whose switch can come 20 min later; an outage nothing explains has `cause: null`. `node bridge/history.mjs data/boxes/paho-gs2000-03` writes it and prints the episodes.
- `bridge/parse.py` takes each output, without its echo and prompt, and turns it into JSON with the TTP template `data/boxes/<box-id>/ttp/templates/<id>.ttp`, where `<id>` is the command's id in `data/cli/csp/cli-index.source.json` (`show och 1-7-5` runs `cli_shortcut_cmds_l1__och__show__och`). `bridge/cli-index.mjs` finds the id, and a command with no template is recorded without a parse. Results keep the CLI's own sections and names:
  - A command for one entity (`show och 1-7-5`, `show transceiver 1-7-4`) gives `{ config: {…}, state: { …, stats: {…} } }`. Its `key value` lines are strings as printed (`"193500000 MHz"`), and its `instant | avg | min | max` lines are numbers (`stats["q-margin"]` is `{ instant: 3.4, avg: 3.4, min: 3.3, max: 3.4, unit: "dB" }`). Its address is in the command, not in the output. These templates are a single `<extend template="_detail.ttp"/>`; `show card` and `show logical-channel` add it for their detail form (`show card 1-7`).
  - A list is keyed by CLI address or name (`state.ports["1-7-5"]`, `config["cross-connections"].CC5_4`, `alarms[<id>]`), or is a list in order where rows have no key (`state.assignments`, `events`). L0 tables are keyed the same way: `state.ports["port-1-1-ad1"].in["optical-power"]` (`show optical-port`), `state.amplifiers["1-1-ba"]` with its measured gain and powers under `stats` (`show amplifier`, with `_stats.ttp`), `thresholds["PORT-1-1-AD1"].IN_OPTICAL_HIGH_WARNING` (`show profile-threshold`).
- `GET /bridge/state?host=` returns the latest result per command for that box's session. While connected it is `{ live: true, host, commands }`, with what the poller read this session: `{ at, raw, data }` (`data` null with no template), or `{ at, raw, error }`. While not, it is `{ live: false, host, run, at, commands }`, the last state on disk of the box last reached at that host: the latest run's snapshot (by `meta.json` `ended`, skipping a run whose snapshot was cut short; a fast one goes over the last full snapshot), each command updated by its last line in `poll.jsonl`, as `{ at, data }`, `{ at, error }`, or `{ at, raw }` with no template. Times are in ms. With no run at that host, it is `{ live: false, run: null, commands: {} }`.
- Set up once with `npm run bridge:setup`, which makes `bridge/.venv` with TTP in it. The bridge won't start without that Python or without the templates in its data root (`ttp/templates`), since every run would then be recorded unparsed.
- **To add a command:**
  1. Copy its output from a run (`data/boxes/<box-id>/runs/<run>/raw/NNN_<slug>.txt`) to `data/boxes/<box-id>/ttp/fixtures/<name>.txt`, where `<name>` is the command's id.
  2. Write `data/boxes/<box-id>/ttp/templates/<name>.ttp`. For a command that shows one entity, `<extend template="_detail.ttp"/>` is the whole template. For a table, copy one row and replace each value with `{{ column-name }}`, as in `cli_shortcut_cmds_l1__port__show__port.ttp`. Give a value a regex when spaces alone can't tell the columns apart.
  3. Put the JSON you expect in `data/boxes/<box-id>/ttp/fixtures/<name>.json`.
  4. Add the command to `poll.json`; its template is found by its id.

  `npm test` checks every template against its fixture. A fixture named `<id>~<form>` tests another form of the same command (a list form and its detail form share an id, so one template parses both). TTP 0.10.1: a `|` inside `re("…")` splits the argument, so write a literal pipe as `\x7c` and put a regex with alternation in the template's `<vars>`, by name (`re("ADMIN")`); `_headers_` fails on hyphenated column names; an indent in a template line is matched literally.

## Runs

`data/boxes/<box-id>/runs/` has a folder per snapshot, with the polls after it until the next one:

```
<YYYYMMDD-HHMMSS>-<trigger>/     connect | alarms | pull | baseline | procedure
  meta.json
  raw/index.jsonl                one line per command, in the order they ran
  raw/NNN_<slug>.txt             the exact output, prompt lines cut
  parsed/NNN_<slug>.json         its TTP result, or { "error": … }
  poll.jsonl                     the polls until the next snapshot
  wiring.csv                     the box's strands when the snapshot began
  answer.json                    a pull only: the strand marked
  procedure.json                 a procedure's first run only: its definition, params, who asked and approved, each step, the outcome, the runs it touched
```

- **File names:** `NNN` is the order the commands ran; the slug is the command with spaces turned into `-`, `*` into `all` and `?` into `help` (`show port 1-7-*` is `004_show-port-1-7-all.txt`).
- **`raw/index.jsonl`:** `{"n": 7, "cmd": "show och 1-7-5", "at": "…", "source": "snapshot", "file": "007_show-och-1-7-5.txt", "ok": true}`. `ok` is true once the prompt came back, so the output is whole. `source` is `prereq`, `snapshot`, `typed`, `mcp` (with `by`, the Codex session that asked), `procedure` (with `by`, `procedure:<id>`) or `hand`. Errors and empty output are kept: they are data.
- **`meta.json`:** `run`, `box`, `host`, `hostname`, `release`, `trigger`, `started`, `ended`, `boxClock`, `boxClockOffsetSec` (the box clock minus the bridge machine's, to line alarm times up with pulls), `prereqs` (`[{ cmd, ok }]`), `state` (`unknown` until labelled `healthy`, `fault` or `restored`), `notes`, and `snapshot: { done, of, fast, workers }`. `done` < `of` means the snapshot was cut short, and the last state skips the run; `fast` means only the polled and `fast` commands ran, so the last state lays it over the last full snapshot.
- Older runs: `run-01-healthy` is the one hand capture, split from a `session.log` by `scripts/split-session-log.mjs` (`source: "hand"`); runs before 2026-11-01 20:40 have no `snapshot`.

## Tests

`npm test` runs everything in `test/`, kept apart from the code it checks: `test/bridge/` for the bridge, `test/src/` for the app's model, and `test/fakes/` for what the tests run against. Nothing in it reaches a box: a test opens a session only through the fake ssh2, on a made-up host, never a real host or IP.

- **Sessions** (`test/bridge/sessions-*.test.mjs`, `endpoints.test.mjs`): the real bridge in the test's own process, with ssh2 swapped for a fake (`test/fakes/ssh2.mjs`) that opens no socket. Its boxes are made up (`box-1.t1.test` …) and their runs go to a temp folder. Six people (physical views and Codex sessions) on one box, and six boxes at once, each held by six: one SSH login and one snapshot a box, whatever the number of people, one box's people never touching another's, the bridge quick to answer, and nothing left open once everyone leaves. Also a box that refuses the login, drops the connection, never answers a command or is slow to prompt; shows, pulls and baselines asked for at once; terminals and terminal windows; procedures (`sessions-procedures`, `-changes`, `-drops`: the tests' own, in `test/fakes/procedures.mjs`, read from a catalog of their own) run, approved, cancelled and dropped; and run files broken by hand, which never take the bridge down.
- **Recorded runs** (`runs.test.mjs`, `templates.test.mjs`, `procedure-checks.test.mjs`, `test/src/smoke.test.ts`, `l0.test.ts`): box 3's runs as `/run` serves them, the light and the L0 path on them, every TTP template against its fixture, and the software audit and health check on each box's latest recorded output. The bridge ones need `npm run bridge:setup`'s Python, and are skipped without it.
- **Units:** each module's corner cases: the CLI index match, tables, the history and its episodes, the recorder, wiring inference, the poller's shells, typed and asked shows, terminal windows, procedure definitions and params, every procedure line against the CLI index and the boxes' logs (`procedure-lines.test.mjs`, shown first to catch made-up lines on procedures of its own), and the app's catalog, rules, discovery, light, routing, store and procedures.

## Choices the plan left open

- **Port roles are inferred** from each port's profile module or name (see [Catalog](#catalog)); a port the sync can't place is a plain `port`. Fix a wrong role in `scripts/sync-linecards-from-iivi.mjs`, not in the generated JSON.
- **A link is one strand**, `a` Tx → `b` Rx; a duplex pair is two links. Files saved before this (when one link meant both strands) open as one strand each, `a` → `b`; add the return strand by hand.
- **Fibers between two cards of one device** are allowed (rule 4) and drawn as a loop under the device. Parallel fibers between two devices are drawn side by side, spread away from the devices. **Loopback** is allowed only on a line port, Tx to its own Rx (no client loopbacks, no port-to-port fibers on one card).
- **Data view** pairs client ports by position (C1↔C1, C2↔C2) on cards whose line ports share a fiber directly, in either direction; a loopback carries no service. No path tracing through amps or muxes; the views are cosmetic, as the plan says.
- **All catalogs ship in one bundle.** See the confidentiality question in the [decision log](decisions.md#open).
- **Alarms are simulated from the build**, since there is no live device: LOS on pluggables with nothing into their Rx and missing PSUs or fans. There are no models of PSU or fan (one generic unit each), no way to fail a unit that is in, and no CLI command for alarms yet.
